## Troubleshooting

### 1. Code changes not taking effect after deploy

**Incident:** 2026-02-15 (4 days of changes not running)

**Symptoms:** Deployed code changes via `git pull` + `docker compose restart`, but
the bot's behavior didn't change. Logs showed old behavior for 4 days.

**Root cause:** The Dockerfile uses `COPY . /app` to bake code into the image at build
time. `docker compose restart` reuses the existing image — it does NOT rebuild.

**Fix:** Always use `--build`:
```bash
docker compose -f docker-compose.aws.yml up -d --build v2-kraken
```

**Prevention:** This is documented in CLAUDE.md, the deployment guide, and SYSTEM_CONTEXT.md.
Never use `docker compose restart` for code changes.

### 2. Phantom positions inflating portfolio balance

**Incident:** 2026-02-27 (commit `7bdbd40`)

**Symptoms:** Starting balance rose from $10,000 to $12,400 despite -$57 actual P&L.
67 phantom sells appeared — sells for positions that didn't exist.

**Root cause:** In `app.py`, `_on_fill_portfolio()` deleted fully-sold positions from the
in-memory dict BEFORE calling `save_position()`. The DB check `if symbol in portfolio.positions`
was already False, so `v2_positions` was never updated to qty=0. On container restart, stale
positions were restored into the paper exchange, allowing phantom sells.

**Fix (two-part):**
1. `app.py` (lines 347-350): Save position with `qty=0` to DB before deleting from memory.
2. `portfolio_tracker.py` (lines 100-106): Cap sell qty at available position during
   `replay_fills()` — skips phantom sells in historical data.

**DB cleanup performed:**
```sql
-- Reset 20 stale v2_positions entries to fill-computed values
UPDATE v2_positions SET qty = 0 WHERE symbol IN (...);
```

**Diagnostic tool:** `scripts/diagnose_portfolio.py` — replays fills, shows cash/positions/discrepancy.
```bash
docker exec -i v2-kraken python < scripts/diagnose_portfolio.py
```

### 3. Exit manager blocking its own stop signals

**Incident:** 2026-02-21 (commit `a1fafc4`)

**Symptoms:** Trailing stops and hard stops weren't firing. The exit manager generated
the sell signal, but then its own `check_signal()` method vetoed it during the risk chain.

**Root cause:** The exit manager publishes a SignalEvent which flows through the normal
risk chain — including back through the exit manager itself. `check_signal()` saw
`_trailing_active=True` for the symbol and returned None (veto), thinking it was an
external signal that would interfere with trailing.

**Fix:** Skip the trailing-active block when `symbol in _pending_exits` — i.e., when the
signal was generated by the exit manager itself.

### 4. LIMIT sell orders stuck on illiquid pairs

**Incident:** 2026-02-21 (commit `07f0638`)

**Symptoms:** Soft stop sell orders were being placed as LIMIT orders on illiquid pairs.
The price would drift away, the stale order logic would cancel them, and the position
would remain stuck — never exiting.

**Root cause:** Soft stops used LIMIT orders. On illiquid pairs, the bid moved away from
the order price before it could fill. The stale drift check then cancelled the order.
The cycle repeated indefinitely.

**Fix:** All stop exits (soft, hard, trailing) now use MARKET orders. Hard stops already
used MARKET; this extended it to soft and trailing stops.

### 5. Junk tokens entering the trading universe

**Incident:** 2026-02-21 (commit `0335868`)

**Symptoms:** Pair discovery included tokens like MYX, USELESS, and AZTEC — extremely
illiquid pairs with wide spreads. These led to bad fills and hard stops.

**Root cause:** Pair discovery filtered only by 24h quote volume. Some junk tokens had
inflated volume numbers but extremely wide bid-ask spreads (>5%).

**Fix:** Added bid-ask spread filter to Kraken pair discovery:
- `max_spread_bps: 100` — rejects pairs with spread > 1.0%
- Spread calculated from Kraken ticker: `(ask - bid) / mid * 10000` bps
- Result: 16 pairs discovered (was 30+ with junk tokens)

**Config:**
```yaml
pair_discovery:
  type: "kraken"
  config:
    max_spread_bps: 100
    shill_coins: ["TRUMP"]
```

To block a specific token, add it to `shill_coins`.

### 6. Reports not sending during quiet periods

**Incident:** 2026-03-15 (commit `1349142`)

**Symptoms:** 4-hour email reports stopped arriving. No errors in logs. System was healthy
and trading normally — just no report delivery.

**Root cause:** The report observer's `_check_period_boundary()` skipped report generation
when no events occurred in the reporting window. During quiet market periods (weekends,
low volatility), zero events meant zero reports.

**Fix:** Generate and send reports even when the event count is zero. A "nothing happened"
report is more useful than silence.

### 7. Report shows $10k/$0 after container restart

**Incident:** 2026-02-21 (commit `60e1132`)

**Symptoms:** First report after a container restart showed starting balance $10,000
and current portfolio $0, even though positions existed.

**Root cause:** `DailyReportV2Observer.start()` initialized the database connection pool
lazily — it wasn't ready when `_check_period_boundary()` captured the first portfolio
snapshot during startup. The snapshot showed empty portfolio because DB hydration hadn't
run yet.

**Fix:** `app.py` now calls `observer.start()` for observers with a `start()` method
during the setup phase, before the main loop begins. This ensures the DB pool is ready
before the first snapshot.

### 8. Cross-period P&L showing $0 for valid trades

**Incident:** 2026-02-21 (commit `60e1132`)

**Symptoms:** Report P&L section showed $0 for sells that were clearly profitable.
Only happened for sells whose corresponding buys occurred before the reporting window.

**Root cause:** `collect_pnl()` computed FIFO P&L only from fills within the reporting
window. If the buy happened 6 hours ago and the sell happened now, there was no buy in
the window to match against → $0 P&L.

**Fix:** `collect_pnl()` now pre-populates buy queues from ALL prior fills (same approach
`collect_trade_log()` already used).

**Caveat:** When passing `prior_queues` to `compute_fifo_pnl()`, wrap in
`defaultdict(deque)` — a plain dict causes KeyError for new symbols not in prior queues.

### 9. Stale exits ejecting profitable positions

**Incident:** 2026-03-15 (commit `671118c`)

**Symptoms:** Positions that were profitable (e.g., +2%) were being closed by `stale_exit`
after the `max_hold_hours` (48h) time limit, locking in a gain that could have been
larger, or worse, exiting at an inopportune moment.

**Root cause:** The `stale_exit` time limit fired unconditionally — it didn't check
whether the position was in profit or loss.

**Fix:** Conditioned `stale_exit` on negative P&L only. Positions in profit are left
for the trailing stop to manage. Unprofitable positions held past 48h are still ejected.

### 10. Zombie positions after pair discovery refresh

**Incident:** 2026-03-15 (commit `ac112ca`)

**Symptoms:** After pair discovery refreshed and dropped a symbol from the active set,
the data provider unsubscribed from that symbol's ticker. The exit manager could no
longer monitor the position (no price updates), so the position sat indefinitely.

**Root cause:** Pair discovery published `SymbolsUpdatedEvent` with the symbol in the
`removed` set. Data providers unsubscribed. But the exit manager still held the position.

**Fix (two-part):**
1. At startup, position symbols are merged into the pair discovery symbol list.
2. Data providers are given a callback (`set_position_symbols_fn`) that returns currently
   held symbols. These are never unsubscribed even if pair discovery drops them.

### 11. Disk space exhaustion on AWS

**Incident:** 2026-02-21

**Symptoms:** Docker builds failing with "no space left on device". Container logs
filling up. AWS t3.medium has only 20GB root volume.

**Root cause:** Docker build cache and old images accumulated over time.

**Fix:**
```bash
docker system prune -af
```
This freed 7.3GB. Safe to run anytime — only removes unused resources.

**Prevention:** Docker log rotation is configured in `docker-compose.aws.yml` (50MB × 3 files).
Keep `.dockerignore` tight to exclude `backtest/data/`, `archive/`, `.git/`.

### 12. Falling-knife buy entries

**Incident:** 2026-02-27 (commit `76ed529`)

**Symptoms:** 12 out of 18 hard stops came from the same pattern: Buy Touch + Buy RSI +
Buy Volume Div firing together. All 12 entered during `downtrend_high_vol` regime.

**Root cause:** These three indicators fire on oversold/mean-reversion signals — they
detect that price is low and volume is fading. But without momentum confirmation, they
catch falling knives in active downtrends.

**Fix:** Trend confirmation gate — require at least 1 trend indicator (Buy MACD, Buy ROC,
or Buy Swing) for composite score buys. This ensures momentum is present, not just
oversold conditions.

**Config:**
```yaml
strategies:
  - type: "composite_scoring"
    config:
      require_trend_for_buy: true
```

**Result:** Trades 139→79, hard stops 18→9, ~$22 in hard stop losses avoided.

### 13. roc_momo_24h causing excessive hard stops

**Incident:** 2026-03-10 (commit `d40f510`)

**Symptoms:** In live paper trading, 8 out of 10 post-Feb-27 hard stops were triggered
by the `roc_momo_24h` entry path. 28% hard stop rate vs. 11% in backtesting.

**Root cause:** The 24h ROC momentum trigger entered during momentum spikes that then
reversed. Multi-symbol trading (28 symbols vs. single-symbol backtest) amplified the
problem — more opportunities to enter at bad times.

**Fix:** Disabled both momentum paths:
```yaml
strategies:
  - type: "composite_scoring"
    config:
      enable_roc_20m_momentum: false
      enable_roc_24h_momentum: false
```

### 14. Regime filter ATR lookback made things worse

**Incident:** 2026-02-27 (commits `27b2e7c` then `c753d38` revert)

**Symptoms:** Tried limiting ATR percentile calculation to a 40-bar lookback window
(instead of full history) to improve regime filtering. Hard stops increased from 18 to 21.

**Root cause:** Hard stops were caused by volatility spikes AFTER entry, not by entries
during high-vol periods. The regime filter was already correctly filtering pre-entry
conditions — a shorter lookback just made it noisier.

**Resolution:** Reverted the change. Regime filter is effective with full-history ATR
percentile. The real fix for hard stops was the trend confirmation gate (see #12).

### 15. roc_momo_20m sell signals firing when entry path is disabled

**Incident:** 2026-04-03 (discovered during live data analysis)

**Symptoms:** 3 out of 8 trades under the current ADX gate config were exited with
`roc_momo_20m` as the signal reason, despite `enable_roc_20m_momentum: false` in the
config. All three resulted in losses or flat outcomes (-$8.26 total). These exits
were not present in backtesting, creating a live-vs-backtest divergence.

**Root cause:** In `strategy.py`, the 20m ROC momentum block (line 288) checks
`enable_roc_20m_momentum` only for the BUY path (line 290). The SELL path (lines 299-307)
is outside that gate — it fires unconditionally whenever ROC < sell_threshold and RSI
is in the sell range. By contrast, the 24h momentum block (line 311) correctly gates
BOTH buy and sell inside the `enable_roc_24h_momentum` check.

**Impact:** Score-triggered positions are being prematurely ejected by momentum sell
signals that the backtest never generated. This is the primary cause of the
live-vs-backtest P&L divergence (-$11.89 live vs +$36.20 backtest).

**Fix:** Wrap lines 299-307 inside the `enable_roc_20m_momentum` check, mirroring the
24h pattern. Must backtest the fix before deploying to confirm no regression.

**Status:** Open — not yet fixed.

## Maintenance Procedures

### Reset paper trading (start fresh)

To zero out all positions and reset to a clean $10k starting balance:

```sql
-- Connect to database
docker exec -it db psql -U bot_user -d bot_trader_db

-- Zero all positions
UPDATE v2_positions SET qty = 0, cost_basis = 0, unrealized_pnl = 0, realized_pnl = 0;

-- Optionally: clear fill history (irreversible)
-- DELETE FROM v2_fills WHERE exchange = 'paper-kraken';

-- Optionally: clear strategy state (resets guardrails, cooldowns)
-- DELETE FROM v2_state;
```

Then restart the container (the paper exchange `initial_balance_usd` in YAML controls
starting cash):
```bash
docker compose -f docker-compose.aws.yml up -d --build v2-kraken
```

### Investigate a specific trade

Given a symbol and approximate time, trace the full lifecycle:

```sql
-- 1. Find the buy fill
SELECT timestamp, symbol, side, price, qty, metadata
FROM v2_fills
WHERE symbol = 'BTC-USD' AND side = 'buy'
  AND timestamp >= '2026-03-10' AND timestamp < '2026-03-11'
ORDER BY timestamp;

-- 2. Find the corresponding sell
SELECT timestamp, symbol, side, price, qty,
       metadata->>'signal_reason' as exit_reason,
       metadata->>'trigger' as trigger
FROM v2_fills
WHERE symbol = 'BTC-USD' AND side = 'sell'
  AND timestamp >= '2026-03-10'
ORDER BY timestamp;
```

For indicator snapshots, check the signal log:
```bash
# On AWS
grep "BTC-USD" /opt/bot/logs/v2_kraken_score_log.jsonl | tail -5 | python -m json.tool
```

### Export trade data for local analysis

```bash
# Fills as CSV
ssh bottrader-aws 'docker exec db psql -U bot_user -d bot_trader_db -c "
COPY (SELECT * FROM v2_fills ORDER BY timestamp) TO STDOUT WITH CSV HEADER
" > /tmp/v2_fills.csv'
scp bottrader-aws:/tmp/v2_fills.csv ./

# Signal log
scp bottrader-aws:/opt/bot/logs/v2_kraken_score_log.jsonl ./

# Positions snapshot
ssh bottrader-aws 'docker exec db psql -U bot_user -d bot_trader_db -c "
COPY (SELECT * FROM v2_positions WHERE qty > 0) TO STDOUT WITH CSV HEADER
" > /tmp/v2_positions.csv'
scp bottrader-aws:/tmp/v2_positions.csv ./
```

### Block a specific trading pair

Add it to the `shill_coins` list in `v2/kraken_paper_trading.yaml`:
```yaml
pair_discovery:
  config:
    shill_coins: ["TRUMP", "BADTOKEN"]
```

Commit, deploy, and the pair will be excluded on the next discovery refresh (every 30 min).

### Rotate Kraken API keys

1. Generate new keys at https://www.kraken.com/u/security/api
2. Update on AWS:
   ```bash
   ssh bottrader-aws
   vi /opt/bot/Config/kraken_api_info.json
   # Replace api_key and api_secret values
   ```
3. Restart (no rebuild needed — key file is mounted, not baked in):
   ```bash
   docker restart v2-kraken
   ```
4. Watch logs for successful WebSocket connection:
   ```bash
   docker logs v2-kraken --tail 20 -f
   ```

### Check if the system is actively trading

```bash
# Quick health check
ssh bottrader-aws "
  echo '--- Heartbeat ---'
  ls -la /opt/bot/logs/v2_kraken/heartbeat
  echo '--- Container ---'
  docker ps --format 'table {{.Names}}\t{{.Status}}' | grep -E 'NAME|v2|db'
  echo '--- Recent fills ---'
  docker exec db psql -U bot_user -d bot_trader_db -c \"
    SELECT timestamp, symbol, side FROM v2_fills ORDER BY timestamp DESC LIMIT 3;
  \"
  echo '--- Signal log lines ---'
  wc -l /opt/bot/logs/v2_kraken_score_log.jsonl
"
```

## System Boundaries

These are known operational limits, not bugs. Documented here so operators know what
to expect.

| Boundary | Value | What Happens When Exceeded |
|----------|-------|---------------------------|
| Container memory | 512MB | OOM kill → container restarts automatically (`unless-stopped` policy) |
| Root disk | 20GB | Docker builds fail. Run `docker system prune -af` to reclaim. |
| Max trading pairs | 30 | Pair discovery caps at 30 (configurable). More pairs = more WebSocket data = higher memory. |
| Report interval | 4 hours | Reports don't fire on demand. Use `python -m v2 report` inside the container for manual generation. |
| Fee cache | 1 hour | Exchange fees are fetched and cached for 1 hour. Fee tier changes take up to 1h to reflect. |
| Pair discovery refresh | 30 minutes | Symbol list updates every 30 min. New listings won't be traded for up to 30 min. |
| Heartbeat interval | 10 seconds | Docker healthcheck expects heartbeat file < 5 minutes old. A 5-minute gap triggers "unhealthy" status. |
| Sell de-duplication | 30 seconds | After a sell is approved, duplicate sell signals for the same symbol are blocked for 30 seconds. |
| Re-entry cooldown | 30 minutes | After exiting a position, the same symbol is blocked from re-entry for 30 minutes. |
| Buy order TTL | 10 minutes | Unfilled buy orders are auto-cancelled after 10 minutes. |
