## Problems Encountered and Solutions

### Problem 1: Sighook Accumulation Manager Not Starting

**Symptoms**:
- Logs showed "Proceeding with sighook setup" repeating every ~12 seconds
- Debug log at line 389 never appeared
- No accumulation manager startup logs
- Code execution appeared to stop after `async_init()`

**Root Cause**:
```python
# Line 388 in main.py (BEFORE FIX)
sighook_logger = logger_manager.get_logger("sighook")  # Returns None!
sighook_logger.info("🔎 [DEBUG] After async_init...")  # AttributeError!
```

The code was reassigning `sighook_logger` with `logger_manager.get_logger("sighook")` which returned `None`, overwriting the valid logger created at line 352. This caused an AttributeError when trying to log, which silently crashed the startup sequence.

**Investigation Process**:
1. Analyzed sighook startup logs looking for patterns
2. Found exception in error logs: `AttributeError: 'NoneType' object has no attribute 'info'`
3. Traced to line 389 in main.py
4. Discovered line 388 was overwriting valid logger from line 352
5. Confirmed `logger_manager.get_logger("sighook")` returns `None` because loggers dict uses different keys

**Solution**:
```python
# Line 388 in main.py (AFTER FIX)
# sighook_logger already created at line 352, don't overwrite it
sighook_logger.info("🔎 [DEBUG] After async_init, about to start background tasks")
```

Removed the logger reassignment since `sighook_logger` was already properly initialized at line 352.

### Problem 2: Leaderboard Job Crashing with AttributeError

**Symptoms**:
```
AttributeError: 'PrecisionUtils' object has no attribute '_usd_pairs'
  File "/app/Shared_Utils/precision.py", line 48, in usd_pairs
    return self._usd_pairs
           ^^^^^^^^^^^^^^^
```

**Root Cause**:
The `PrecisionUtils.__init__()` method never initialized the `_usd_pairs` attribute. It was only set later via `set_trade_parameters()`. The leaderboard job runs independently and creates its own PrecisionUtils instance without calling `set_trade_parameters()`, causing the AttributeError when accessing the `usd_pairs` property.

**Investigation Process**:
1. User reported error from leaderboard job logs
2. Examined PrecisionUtils class structure
3. Identified missing initialization in `__init__`
4. Recognized singleton pattern needed lazy initialization

**Solution**:
```python
# In __init__ (line 28-29):
# Initialize _usd_pairs to None (set later via set_trade_parameters)
self._usd_pairs = None

# In usd_pairs property (lines 51-60):
@property
def usd_pairs(self):
    if self._usd_pairs is None:
        # Try to load from shared_data_manager if available
        if self.shared_data_manager:
            usd_pairs = self.shared_data_manager.market_data.get('usd_pairs_cache')
            if usd_pairs is not None and not usd_pairs.empty:
                self._usd_pairs = usd_pairs
                return self._usd_pairs
        # Return empty DataFrame if not available
        import pandas as pd
        return pd.DataFrame()
    return self._usd_pairs
```

**Key Changes**:
1. Initialize `_usd_pairs = None` in `__init__`
2. Add lazy loading in property getter
3. Fallback to empty DataFrame if data unavailable

**Deployment**:

## Important Findings

### Logger Management Pattern:
The codebase has two logger creation patterns:
1. `get_logger('main', context={...})` - Creates standalone logger (line 352)
2. `logger_manager.get_logger("name")` - Retrieves from loggers dict

**Key Insight**: The two systems use different naming conventions. Mixing them can result in None returns.

### Docker Image Caching:
`docker restart` reuses existing container images. Code changes require:
1. `git pull` to update source
2. `docker compose build <service>` to rebuild image
3. `docker compose up -d <service>` OR `docker start <service>` to run new image

### Singleton Lazy Loading Pattern:
For singleton utility classes accessed from multiple contexts (main bot, jobs, scripts), initialize all attributes to None in `__init__` and use property-based lazy loading with graceful fallbacks.

### LOG_LEVEL=DEBUG Impact:
- Console/Docker logs: Shows ALL debug messages when set to DEBUG
- File logs: Always capture DEBUG regardless of env setting (by design)
- Recommendation: Change to INFO after system stability confirmed

3. **Check logger creation**: Ensure loggers aren't being overwritten with None
4. **Verify Docker rebuild**: Code changes require image rebuild, not just restart
