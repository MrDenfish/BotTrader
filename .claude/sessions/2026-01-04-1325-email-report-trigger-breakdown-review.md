### Problem Identified

**Issue:** Trigger Breakdown section showing "LIMIT" for all orders
- Current report displayed: `Trigger: LIMIT | Orders: 4 | Wins: 0 | Losses: 0`
- Expected: Breakdown by strategy type (Signal Matrix, ROC, Passive MM, etc.)

**Root Cause:**
- `trigger` field in `trade_records` table stores order type ("limit") not strategy trigger
- WebSocket order recording doesn't preserve original strategy trigger metadata
- Query was extracting from wrong field: `trigger->>'trigger'` returned "LIMIT" or "limit"

### Solution Implemented

**Approach:** Infer trigger type from buy order size (notional value)

Order size to trigger mapping:
- $13-17 → Signal Matrix (ORDER_SIZE_SIGNAL)
- $18-23 → ROC Momentum (ORDER_SIZE_ROC)
- $24-30 → Webhook/External (ORDER_SIZE_WEBHOOK)
- $31-34 → Passive MM (ORDER_SIZE_PASSIVE)
- Other → Websocket (manual/external)
- Preserve TP/SL exits from database

**Changes Made:**
1. Modified `botreport/aws_daily_report.py:query_trigger_breakdown()`
2. Added `buy_orders` CTE to infer trigger from order size
3. Joined sell orders to buy orders via FIFO allocations
4. Updated query logic to use inferred triggers

## Bonus: Trigger Preservation Improvement Plan

**Created:** `docs/TRIGGER_PRESERVATION_IMPROVEMENT_PLAN.md`

Comprehensive outline for improving trigger metadata preservation from order placement through WebSocket recording. The plan includes:

### Three-Phase Approach

**Phase 1: Fix In-Memory Cache (Quick Win - 2-3 hours)**
- Improve ID matching for cache lookups
- Implement delayed cache cleanup (5-minute window)
- Enhanced logging for diagnostics

**Phase 2: Database Persistence (Medium-term - 4-6 hours)**
- Create `order_metadata` table for long-term storage
- Persist trigger metadata on order placement
- Database lookup fallback for cache misses
- Survives session restarts

**Phase 3: Enhanced Reporting (Long-term - 2-3 hours)**
- Use real trigger values in reports
- Show specific indicators (RSI, MACD, BB, etc.)
- Detailed trigger performance breakdown

### Key Benefits

1. **Preserve exact trigger values** (rsi_oversold, ROC_MOMO, macd_cross)
2. **Survive session restarts** via database persistence
3. **Granular performance analysis** by specific indicator
4. **Audit trail** for all trades
5. **Enable strategy optimization** based on real data

### Root Causes Identified

1. **ID Mismatch**: Cache uses different ID format than WebSocket fills
2. **Premature Cleanup**: Cache deleted immediately after first lookup
3. **No Database Fallback**: Only in-memory cache, no persistence
4. **Session Boundaries**: Data lost on container restart

### Implementation Includes

- Detailed code examples for each phase
- Database schema and migration scripts
- Testing strategy (unit, integration, manual)
- Monitoring metrics and alerts
- Rollback plan and success criteria
- Estimated effort: 12-18 hours total

This plan provides a clear roadmap to move from size-based trigger inference to actual trigger preservation.

## client_order_id Investigation (Elegant Solution)

**Date:** 2026-01-04 (continued)
**Time:** 14:30 PST

### Discovery: client_order_id Already Available

After enabling the Coinbase MCP server, investigated whether `client_order_id` could provide an elegant alternative to the 3-phase database persistence plan.

### Key Findings

✅ **client_order_id is ALREADY in our codebase:**
- **Generated at:** `webhook/webhook_order_types.py:797`
- **Current format:** `{source}-{uuid8}` (e.g., "PassiveMM-90ed34f3")
- **Preserved in:** WebSocket user channel events (confirmed in archived data)

✅ **Evidence from archived order data:**
```json
{
  "order_id": "e276c43b-37c1-4d30-ba7f-b7d0dcbac293",
  "client_order_id": "PassiveMM-90ed34f3",  // ← Present in WebSocket events
  "status": "FILLED",
  ...
}
```

✅ **Available in WebSocket flow:**
- Order placement: Sets `client_order_id` in Coinbase API request
- WebSocket user channel: Returns full order object including `client_order_id`
- Currently: **We're NOT using this field in WebSocket processing**

### Current Code Generation

**Location:** `webhook/webhook_order_types.py:797`
```python
"client_order_id": f"{order_data.source}-{uuid.uuid4().hex[:8]}",
```

**Current values:**
- `{source}` = "webhook", "PassiveMM", "sighook", "websocket", etc.
- `{uuid8}` = 8-character random UUID

### The Elegant Solution

**Instead of 3-phase database persistence, we can encode trigger directly in client_order_id:**

**Proposed format:**
```python
"client_order_id": f"{trigger_type}-{symbol}-{uuid.uuid4().hex[:6]}"
```

**Examples:**
- `"RSI_OVERSOLD-BTC-a1b2c3"` → Signal Matrix RSI indicator
- `"ROC_MOMO-ETH-d4e5f6"` → ROC Momentum strategy
- `"PASSIVE_BUY-DOGE-g7h8i9"` → Passive Market Making
- `"MACD_CROSS-ADA-j0k1l2"` → Signal Matrix MACD indicator

**Benefits:**
1. ✅ **No database changes needed** - Uses existing field
2. ✅ **Survives session restarts** - Encoded in Coinbase order
3. ✅ **No cache required** - Parse from client_order_id in WebSocket handler
4. ✅ **Audit trail preserved** - Visible in Coinbase Advanced Trade UI
5. ✅ **Zero infrastructure overhead** - Just string parsing
6. ✅ **Immediate implementation** - ~30 minutes vs 12-18 hours

### Implementation Steps

**Step 1: Encode trigger in client_order_id (webhook/webhook_order_types.py)**
```python
# Extract trigger type from order_data.trigger
trigger_type = "UNKNOWN"
if isinstance(order_data.trigger, dict):
    trigger_type = order_data.trigger.get("trigger", "UNKNOWN").upper()
elif isinstance(order_data.trigger, str):
    trigger_type = order_data.trigger.upper()

# Generate client_order_id with trigger encoded
client_order_id = f"{trigger_type}-{symbol.split('-')[0]}-{uuid.uuid4().hex[:6]}"
```

**Step 2: Parse client_order_id in WebSocket handler (webhook/websocket_market_manager.py)**
```python
# In _build_trade_dict() or _build_fill_dict()
client_order_id = order.get("client_order_id", "")
if client_order_id:
    parts = client_order_id.split("-")
    if len(parts) >= 3:
        trigger_type = parts[0]  # e.g., "RSI_OVERSOLD", "ROC_MOMO"
        trigger = {
            "trigger": trigger_type.lower(),
            "trigger_note": f"Decoded from client_order_id: {client_order_id}"
        }
```

**Step 3: Remove in-memory cache dependency**
- Cache becomes optional fallback for backwards compatibility
- New orders use client_order_id parsing
- Gradual migration as old orders complete
